# On-device ML for WorldKey

A plan for adding learned models to the engine. Everything runs on the user's Mac. Keystrokes,
words and model updates never leave it; the app makes no network requests.

## Decision

Add two small models and keep every rule that already works.

1. **A character language model per language.** Smoothed character 4-grams, shipped as compact
   tables in plain Swift. It becomes one more evidence source next to the spell checker. It covers
   the languages that have no system dictionary.
2. **A logistic-regression combiner.** It replaces the hand-tuned weights in `Scorer` with weights
   fitted on synthetic data, then nudges them on the user's own corrections, on the device.

No neural network, no Core ML model file, no MLX, and no Foundation Models in the typing path.
Reasons are under "Rejected".

## Why learn anything

The rule engine is good where it has a dictionary. `worldkey eval` reports no false fixes on 150
words per language, 82–100% of wrong-keyboard words fixed, and 0.13 ms per word. It fails in four
places:

- **No dictionary.** Thai, Khmer, Lao, Georgian, Armenian, Myanmar, Tibetan, Sinhala and most of the
  251 layouts. There `Scorer` gives −0.5 for "unknown" and relies on `Orthography`, so auto-fixing
  almost never fires. The convert shortcut does the work.
- **Names and slang.** "Oddur", "lol" and "þú veist" are not dictionary words. They score as
  misspellings and lose close calls.
- **Mid-word.** `decidePrefix` asks only whether any word starts this way. It cannot say that a
  prefix is *unlikely*, so it waits for the impossible.
- **Hand weights.** The +3, −1, −2 and −0.5 in `Scorer` were tuned by eye on a handful of pairs.
  Nothing says they are right for Arabic against French.

Each failure is the lack of a graded "how much does this look like language X" signal. A character
model supplies it for every script. A combiner weighs it against the rest.

## The key insight: labeled data is free

The engine can already generate labeled examples for any pair of keyboards.
`KeyLayout.strokes(for:)` turns a word into keys on its own layout. Every other keyboard reads
those keys as its wrong-layout version. All 251 layouts round-trip, and so do Korean and
Vietnamese through their composers. So for any word list and any pair (A, B):

- `(A.text(keys), typed on A)` is a negative: leave it alone.
- `(B.text(keys), typed on B, meant A)` is a positive: fix it to A.

This gives unlimited, exactly labeled data for every layout pair, with no human labeling and no
user data. It is how `Evaluation` already works; training reuses it.

## Model 1: character language model

- **Unit.** Unicode scalars after NFC, lowercased, with `^` and `$` boundary marks. Scalars rather
  than grapheme clusters, so Indic and Thai marks are seen individually. Malformed mark order is
  exactly the evidence wanted.
- **Order and smoothing.** Interpolated Kneser–Ney, order 4, with stupid backoff for unseen
  contexts. Short words carry little evidence, and 4 characters of context covers most of a word.
- **Output.** The mean log-probability per scalar, minus the same under a uniform-over-script
  background. That gives `naturalness(text, language)` in nats, comparable across languages.
  `prefixNaturalness` is the same score without the `$` mark, for mid-word use.
- **Storage.** A minimal perfect hash of the n-grams kept after pruning, with log-probs quantized
  to 8 bits. Target: under 300 KB per language, memory-mapped, and loaded only for enabled
  keyboards.
- **Training data.**
  - Languages with a system dictionary: the spell checker's own word list, enumerated with
    `completions` the way `Evaluation.sample` does. It is generated by `worldkey train` on the
    developer's Mac and frequency-weighted by completion rank.
  - Languages without one: a public corpus per language, Leipzig Corpora Collection or Wikipedia
    text, with the license recorded beside each table. The build reads the corpus; the app never
    does.
- **Where it plugs in.** A new `CharacterModel` type in `WorldKey`, behind the `Lexicon` protocol
  as `naturalness(_:language:) -> Double?`. It is nil when no table exists, as `isWord` is today.

## Model 2: the combiner

`Scorer` turns into feature extraction. For a candidate pair (current reading, other reading), it
emits the differences:

| Feature | Source |
|---|---|
| lexicon validity: +1 / 0 / −1, per side | `isWord` with exact completion |
| prefix validity | `startsWord` |
| orthography penalty | `Orthography.penalty` |
| symbols inside the word, trailing punctuation | `Scorer.trim` |
| alphabet mismatch count | CLDR exemplars |
| character-model naturalness, per side | Model 1 |
| recognizer delta, same-script only | `Scorer.recognition` |
| confusion boost | `Memory.boost` |
| word length, capitalized, target kind | strokes, `KeyboardKind` |

P(meant the other keyboard) = σ(w · x + b). That is about 30 weights.

- **Offline fit.** Fit on synthetic pairs with L2 regularization. Negatives are weighted 20:1, so
  the fitted boundary sits on the cautious side.
- **Thresholds.** Sensitivity levels are probability cut-offs chosen on held-out data. *Cautious*
  allows no false fix on the gate set; *Balanced* matches today's false-fix rate (zero on the gate)
  with higher recall; *Eager* trades a measured false-fix rate for recall, and the setting shows
  that rate.
- **Hard guards stay outside the model.** Addresses and paths, user exceptions, converting sources,
  learned words and secure input are rules, not features. No weight can override them.
- **Shipping.** The weights ship as a JSON resource of a few hundred bytes, so the model can be
  read and diffed in review.

Phase 0 below proves the refactor first: hand weights expressed as a feature vector must reproduce
today's scores exactly.

## On-device personalization

The app already sees labeled events. Today they feed `Memory`. They will also feed the combiner:

| Event | Label | Weight |
|---|---|---|
| Erase, switch, retype the same keys (`Retype`) | positive | 1 |
| Convert-last-word shortcut | positive | 1 |
| ⌘Z or shortcut right after an auto-fix | negative | 2 |
| Auto-fix left standing through the next word | weak positive | 0.3 |
| Word typed, not fixed, not erased (sampled 1 in 20) | weak negative | 0.1 |

- **Update rule.** Online logistic-regression SGD with a small learning rate and an L2 pull toward
  the shipped weights. The personal weights stay a bounded delta: each weight is clamped to ±50% of
  its shipped value. A user can sharpen the model but cannot teach it to fix everything.
- **Personal vocabulary.** It takes names and slang out of the "misspelling" bucket. Words typed
  and kept on a keyboard, three times or more, get a per-language count. They are stored as salted
  hashes of their key signature, never as text. There are at most 5,000 entries, halved monthly as
  `recordUse` already does for apps. Lookup adds one feature: "you write this here."
- **Where it runs.** Updates go to a serial background queue after the word ends and are batched
  every 20 events. Nothing trains inside the event tap.

## Budgets

| | Budget | Check |
|---|---|---|
| Judge one word, p99, 4 candidate keyboards | ≤ 0.3 ms | `PerformanceTests`, new |
| Event tap work per key | unchanged | no model call on non-boundary keys unless fix-while-typing |
| Resident memory, 4 enabled languages | ≤ 2 MB extra | Instruments, once per release |
| Disk, all shipped tables | ≤ 25 MB | build script fails above it |
| Personal state | ≤ 300 KB | capped counts, clamped weights |

A character-model lookup is a hash probe per scalar. Four candidates times about 10 scalars is
about 40 probes, well under 50 µs. The combiner is 30 multiply-adds. The spell checker stays the
slowest part, and its verdicts are cached.

## Privacy

- **Stored.** Everything lives in `~/Library/Application Support/LangSmart/`, mode 0600:
  - `memory.json`: what exists today. Learned corrections keep their keys so Settings can list and
    delete them; the user sees exactly what is kept.
  - `model.json`: the personal weight deltas, 30 numbers.
  - `vocabulary.bin`: salted signature hashes and counts. No text.
- **Never stored.** Raw keystrokes, sentences, words merely typed, timestamps beyond what decay
  needs, and anything from secure input fields, which the tap never sees.
- **Deleting.** "Forget Everything" in Settings → Learning removes all three files. A new "Reset
  learned model" removes `model.json` and `vocabulary.bin` only.
- **Network.** None. No telemetry and no model downloads. The README states this, and a test
  asserts the app binary links no networking API.

## Evaluation gates

`worldkey eval` grows into the gate. It keeps the rule engine as a baseline flag:

    worldkey eval --engine rules|model --split heldout --keyboards …

- **Held-out split.** Words are assigned to train or test by a hash of the word, so no evaluation
  word was ever seen in training. Pairs share the split.
- **Gate set.** 150 words per language, held out. It covers 12 fixed pairs: the eight in the README,
  plus U.S. with Thai, Georgian, Armenian and Khmer.
- **Pass.** Zero false fixes at *Cautious* and *Balanced*. Recall per pair no more than 1 point below
  the rule baseline. Recall of at least 80% on the four no-dictionary pairs, where the rules sit near
  zero today.
- **Names.** A list of 500 personal names, typed on the right keyboard. It must produce zero false
  fixes.
- **Personalization replay.** A scripted session that corrects one slang word three times must
  have it fixed on the fourth. After 500 random corrections, the gate must still pass. The clamp is
  what this tests.
- **CI.** It runs the gate on `macos-26`. Tables are rebuilt only when inputs change.

## Phases

| # | Work | Done when |
|---|---|---|
| 0 | `Scorer` emits a feature vector; hand weights become a weight vector | Every existing test and the eval numbers are identical |
| 1 | `worldkey train` generates synthetic pairs and fits the combiner on existing features | Gate passes; recall ≥ baseline on every pair; weights checked in |
| 2 | Character model: trainer, table format, `naturalness` evidence | No-dictionary pairs ≥ 80% recall, zero false fixes; latency budget holds |
| 3 | Prefix features for fix-while-typing | Prefix precision 100% on the gate; setting stays off by default until tried in real apps |
| 4 | Personalization: event labels, online updates, personal vocabulary | Replay tests pass; gate still passes after adaptation; Reset works |
| 5 | Settings: model on/off, reset, the measured false-fix rate per sensitivity | Values shown come from the shipped eval report |

Each phase is one pull request and is useful alone. Phase 1 can ship even if phase 2 slips.

## Rejected

- **Foundation Models (the on-device system LLM).**
  - It needs Apple Intelligence enabled and the model downloaded.
  - It has a 4,096-token context.
  - A session takes 200–500 ms to start.
  - It is a general text model, not a keyboard model.
  - It is too slow and too often missing for a per-word decision. It might later check a selected
    sentence on request, off the typing path, but that is not this plan.
- **MLX.** It is a research framework and would be a large dependency for a 30-weight model. It
  could be the trainer if the model ever grows into a neural network. It is not the runtime.
- **Core ML or Create ML text classifiers.**
  - Calling a model per word costs more than a hash probe.
  - The maximum-entropy and BERT text classifiers target sentences, not keyed fragments.
  - Updatable models in `MLUpdateTask` are documented for other model types, so on-device updates
    to a text classifier are not established.
  - Plain Swift keeps the engine dependency-free and the model readable.
- **fastText lid.176.** It covers 176 languages in 917 KB but was trained on sentences. It sees the
  script, not the layout, which is the recognizer's failure again.

## Risks, and where this plan is weakest

- **Synthetic is not real.**
  - Real mistakes mix typos with wrong layouts.
  - People switch layout mid-word.
  - Real text is capitalized and full of names.
  - The generator produces clean dictionary words only.
  - Mitigation: add typo noise (one substitution, deletion or transposition) to a share of the
    pairs, and keep the names gate. There will still be no field data, by design.
- **Corpora for no-dictionary languages.** Quality and licenses vary. Wikipedia is CC BY-SA, and
  shipping derived n-gram tables needs attribution. This is the weakest part. If no suitable corpus
  exists for a language, it stays on rules and the shortcut.
- **Dictionaries drift.** The spell checker's lists differ between macOS versions. Tables built on
  the developer's Mac may disagree with the user's. Because the combiner sees both features, a
  mismatch costs recall, not false fixes. The gate should run on each new macOS.
- **Personalization drift.** A user who undoes rarely and converts often pushes the model toward
  eagerness. The clamp bounds this, but the right clamp width is a guess until tried on real
  sessions.
- **The zero-false-fix claim** holds on 150 words per language sampled from the spell checker's
  completions. Those lean toward common prefixes. It is a gate, not a proof.
